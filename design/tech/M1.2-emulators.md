## 1. Versions and decisions

| Package | Where | Version | Note |
|---|---|---|---|
| firebase-tools | root devDep | **15.32.1 (exact)** | Pinned so every machine runs the same emulators; npm scripts use `node_modules/.bin/firebase`, not the global 15.28.1. 15.33.0 (`latest`) was published today, so we take the previous release. Stack-implied tooling: log it in PROGRESS.md. |
| firebase-functions | functions dep | ^7.4.0 | latest. Peers `firebase-admin ^11 … ^14`. Its other peers (graphql, @apollo/server, @as-integrations/express4) are optional. |
| firebase-admin | functions dep | ^14.5.0 | latest. Engines `node >=22`. |
| typescript | functions devDep | ~5.9.3 | Same as root (see M1.1). |
| @types/node | functions devDep | ^24 | |

- **Runtime: `nodejs24`.** firebase-tools 15.32.1 lists nodejs20/22/24 as GA (nodejs20 is decommissioned 2026-10-30). Node 24 is the newest, and it matches local Node 24, so the emulator logs `Using node@24 from host` and there is **no mismatch**.
- **Known future mismatch:** `firebase-functions-test@3.5.0` (a later task) peers `firebase-admin` only up to `^13`. Resolve it when we add it.
- **npm 11 install scripts. Policy: deny.** In npm 11.17, `allowScripts` is advisory for *unreviewed* packages: the install only prints a notice, and the script **runs**. The first prototype really did build `re2.node` with node-gyp. So we record explicit denials with `npm deny-scripts`, which writes name-only `false` entries into `allowScripts` in that package.json. npm 11.17 skips a denied package's script at install time. This was checked in the scratchpad: after the deny, a clean `npm ci` leaves no `node_modules/re2/build/`.
  - Root: `protobufjs` (its postinstall only prints a version-scheme warning), `re2` (an optional native regex used by superstatic, which falls back to JS `RegExp`) and `unrs-resolver` (from M1.1, via eslint-config-next's import resolver; its postinstall is only a network fallback that fetches a native binding, and the binding `@unrs/resolver-binding-win32-x64-msvc` already arrives as an optional dependency).
  - `/functions`: `protobufjs` (same reason) and `@firebase/util` (its postinstall only bakes `FIREBASE_WEBAPP_CONFIG` into a stub for App Hosting auto-init; we never set that variable, and the shipped stub returns `undefined`).
  - The emulator checks in section 6 run with these denials in place. Log the policy in PROGRESS.md. Any new package with an install script must be approved or denied explicitly; `npm approve-scripts --allow-scripts-pending` lists them.
- **`/functions` is a separate npm package** with its own `package-lock.json`, not an npm workspace. Deploy uploads `functions/` and installs from its own manifest; hoisting would break that.
- **Lint:** the root `eslint .` already covers `functions/src/**` (only `functions/lib/**` is ignored). Verified clean with the root config, so functions has no ESLint config of its own. **Format:** the root Prettier already covers it (`functions/lib` is in `.prettierignore`).
- **Typecheck:** `functions/tsconfig.json` is the source of truth (root tsconfig excludes `functions`). The root `typecheck` script also runs it.
- **Predeploy:** `npm --prefix functions run build`. firebase-tools (`lib/deploy/lifecycleHooks.js`) runs each hook through `cross-env-shell`, with `cwd` = project root and `RESOURCE_DIR` set in the env, so the usual `"$RESOURCE_DIR"` form would expand too. We keep the plain relative path for two reasons. First, cwd is always the root, so `functions` resolves correctly. Second, the path has no inner quotes: firebase-tools backslash-escapes every `"` in a hook before wrapping the hook in its own quotes, and that escaping is the fragile part on Windows. This was **simulated, not deployed**: section 6 runs the same `node cross-env-shell.js "<hook>"` call from the root. **Never run deploy.**
- **Trivial function `health`:** a GET-only HTTPS function that returns the constant `{"status":"ok"}` with `Cache-Control: no-store`. Other methods get 405. It reads no Firestore, Auth, env, headers or body, and sends no CORS headers, so nothing can leak, and an HTTP probe can verify it. It sets `cors: false` explicitly: without it, the Functions emulator's debug `enableCors` reflects any `Origin` back in `access-control-allow-origin`, which production does not do. With it, the emulator matches production (verified: a GET with `Origin: https://evil.example` gets no `access-control-allow-origin`). `setGlobalOptions({ maxInstances: 10 })` caps cost. The region stays the default `us-central1` until a real project exists.

## 2. Ports (fixed range 6100–6109, all bound to 127.0.0.1)

| 6100 hub | 6101 UI | 6102 logging | 6103 functions | 6104 firestore | 6105 firestore websocket | 6106 auth | 6107 storage | 6108 eventarc | 6109 tasks |
|---|---|---|---|---|---|---|---|---|---|

Mary project holds 4000/4400/4500/8080/9099/9150. `netstat -ano` shows nothing on 6100–6119, and `netsh … excludedportrange` shows no Hyper-V exclusions. None of these ports is on Chrome's unsafe-port list. Eventarc and Tasks **start automatically with the Functions emulator** (seen in the prototype), so we pin them too; otherwise they would take the defaults 9299/9499. The **Extensions emulator also starts automatically** with Functions. It has no port of its own: it shares the Functions port 6103 and appears in the hub list as `extensions` on 6103. So the hub lists **10 entries**: hub, ui, logging, extensions, functions, firestore, auth, storage, eventarc, tasks. 6110–6119 are reserved for future emulators. One port can't be pinned: the functions SDK opens a short-lived discovery server on a random port (`Serving at port 8xxx`) while it loads definitions. `singleProjectMode: true` only **warns** when a request names a different project ID; it does not refuse it (QA saw a Firestore write to `projects/real-proj` return 200, with a warning in `firestore-debug.log`). Isolation from real projects comes from the `demo-` project ID and the emulator-only hosts, not from this flag.

// Cap scale-out for every function in this codebase (cost guard).
setGlobalOptions({ maxInstances: 10 });

/**
 * Liveness probe. Returns a constant body: no Firestore, Auth, env or request data.
 * `cors: false` stops the emulator from reflecting any Origin, so it matches production.

export const health = onRequest({ cors: false }, (req, res) => {
  if (req.method !== "GET") {
    res.set("Allow", "GET").status(405).end();
    return;
  }
  res.set("Cache-Control", "no-store").json({ status: "ok" });
});

## 4. Root package.json

Add devDependency `"firebase-tools": "15.32.1"` (`npm install -D -E firebase-tools@15.32.1`), then run `npm deny-scripts protobufjs re2 unrs-resolver`. That gives `"allowScripts": { "protobufjs": false, "re2": false, "unrs-resolver": false }`. Scripts to add or change:

| Script | Command |
|---|---|
| postinstall | `npm run functions:install` |
| functions:install | `npm --prefix functions ci` (runs automatically through `postinstall`; run it by hand after a functions lockfile change or after an install with `--ignore-scripts`) |
| functions:build | `npm --prefix functions run build` |
| emulators | `npm run functions:build && firebase emulators:start --project demo-starflames --import=./emulator-data --export-on-exit=./emulator-data` |
| typecheck (changed) | `next typegen && tsc --noEmit && npm --prefix functions run typecheck` |

**Fresh clone: a `postinstall`, not just a doc note.** Root `typecheck` and `emulators` call the `tsc` inside `/functions`, which does not exist until `/functions` is installed. On a fresh clone they would fail with an unhelpful `'tsc' is not recognized`. A root `postinstall` makes a plain `npm install` or `npm ci` leave the repo ready, so QA, CI and the user have no extra step to forget. The script is cross-platform (`npm` plus `--prefix`, no shell syntax), and it does not recurse: the nested `npm ci` runs only the lifecycle of `/functions`, which has no install scripts of its own. It uses `ci`, so the install is reproducible from the committed `functions/package-lock.json` and fails loudly if that lockfile is out of sync. The cost is that every root `npm install` also reinstalls `/functions`, which takes a few seconds. To opt out, install with `--ignore-scripts`, then run `npm run functions:install`.

Every script is a single binary plus `&&`, with no env prefixes, globs or `rm`, so it works in cmd, PowerShell and Git Bash. `--import` of a missing `emulator-data/` starts empty, with no error (verified), and the first exit creates the folder. `/emulator-data/`, `/functions/lib/`, `node_modules/`, `.env*` and `*-debug.log` are already git-ignored (M1.1), so **.gitignore needs no change**. Ctrl+C on Windows: firebase prints "Received SIGINT … clean shutdown", then exports. cmd also asks `Terminate batch job (Y/N)?`. Wait for "Export complete" and the shutdown lines, then answer either way; the export does not depend on that prompt. First-run note: the emulators download their JARs and the UI bundle once into `~/.cache/firebase/emulators`. After that, everything runs offline, with no login and no real project.
